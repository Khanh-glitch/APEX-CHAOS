# A1.0 — Architecture & Migration Audit

**Scope:** Player Account, Economy & Fighter Experience (A1), audited on `main`
at `69b09cf` (PR #95 + PR #96 merged). This document records the *actual*
production authorities found in the repository before any A1 code was written,
the target architecture, the database design, the threat model and the legacy
migration plan. It is the A1.0 deliverable; implementation checkpoints A1.1–A1.6
build on it without introducing competing authorities.

### Pre-A1 defects against the approved product rules

1. `OWNER_PLAYTEST_CORE_SIX_UNLOCK = true` makes every playable fighter
   selectable by every player (selection only; ownership untouched).
2. `OWNER_PLAYTEST_AC_SEED = 12000` overwrites any profile's balance to
   12,000 AC once per revision — including brand-new players.
   `PRODUCT_ECONOMY.cleanStateCredits = 12000` mirrors the override.
3. `awardBattleResult` pays by `winnerSide === 'P1'` only (50/25) and does
   not distinguish BOT from LOCAL. The brief's table (BOT win 100, BOT loss 25
   provisional, LOCAL completed 50 either winner) is not implemented.
4. Reward idempotency is an in-memory flag (`productResultAwarded`) only —
   no persistent claim key survives reload/duplicate callbacks.
5. Ctrl+Shift+F8 and `apexLaunchArsenalLab()` are unauthenticated.
6. Home profile chip (`.profileIdentity`) is decorative; `account-profile`
   surface is LOCKED; there is no account system, no backend, no env config
   (Netlify static hosting only, no functions, no `VITE_*` variables).

### What is already correct and must not regress

- Fresh-state defaults (350 AC, ROBOT-only) exist underneath the overrides.
- `sanitize()` preserves historic balances/ownership; NEWBIE→ROBOT migration
  is idempotent. A1 migration keeps both properties.
- One economy state, one `apex:credits` announcement per save.
- Lucky Draw pool uses `owns()` (production truth), never the override.
- F2 Story lock derives from the registry; A1 does not touch it.

## 2. Target architecture

```
┌──────────────────────────── Browser (Gold product) ────────────────────────────┐
│ src/game/productSurface.js ── availability/roster (unchanged authority)         │
│ src/game/playerAccount.js  ── APEX_PLAYER_ACCOUNT: guest profile + session      │
│                               projection + sync status (NEW, thin)              │
│ src/game/adminAuthority.js ── APEX_ADMIN_AUTHORITY: role derivation (NEW)       │
│ src/game/cloudAccount.js   ── Supabase adapter, env-gated, lazy (NEW)           │
│ src/ui/AccountCenter.jsx   ── Gold Account Center overlay (NEW, presentation)   │
│ arsenalMetaRuntime.js      ── THE wallet/ownership authority (unchanged owner)  │
│ goldProductBridge.js       ── + BRIDGE.skillDetailsFor() read-only projection   │
│ ui/skillDetailsRuntime.js  ── P1/P2 SKILL DETAILS UI (NEW, presentation only)   │
└────────────────────────────────────────────────────────────────────────────────┘
                                   │ HTTPS (anon key + user JWT, RLS)
                                   ▼
┌──────────────────────── Supabase (owner-provisioned) ──────────────────────────┐
│ Auth: Google OAuth, Email OTP, anonymous→link upgrade                          │
│ Postgres + RLS: profiles, wallets, wallet_ledger, fighter_ownership,           │
│   match_reward_claims, player_progress, account_roles, audit_events           │
│ RPC (security definer, idempotency-keyed): claim_match_reward, lucky_draw,     │
│   buy_fighter, migrate_guest_snapshot — SHIPPED DISABLED for wallet issuance    │
│   until server-validated match receipts exist (see §5 trust boundary).         │
└────────────────────────────────────────────────────────────────────────────────┘
```

**Authority discipline:** the wallet that gameplay reads/writes in this phase
remains `APEX_ARSENAL_META` (local). The cloud mirrors identity, profile,
preferences and *snapshots* of progress; it does **not** become a second
spendable wallet until reward receipts can be validated server-side. No module
other than `arsenalMetaRuntime` mutates credits or ownership. Account Center
and skill-details are pure presentation over existing authorities.

## 3. Database schema (migration `supabase/migrations/0001_a1_player_accounts.sql`)

- `profiles (id uuid PK → auth.users, display_name, avatar_url, created_at, updated_at)`
- `account_roles (user_id PK, role text check in ('player','admin'), granted_by, granted_at)` — written only via SQL/service role, never by users.
- `wallets (user_id PK, credits bigint ≥ 0, version int, updated_at)`
- `wallet_ledger (id uuid PK, user_id, delta, balance_after, kind, idempotency_key unique, meta jsonb, created_at)`
- `fighter_ownership (user_id, fighter_id, source, acquired_at, PK(user_id, fighter_id))`
- `match_reward_claims (claim_key PK, user_id, mode, outcome, amount, created_at)` — unique claim key = the idempotency anchor.
- `player_progress (user_id, namespace, version int, payload jsonb, updated_at, PK(user_id, namespace))` — BOT WAVE / preferences snapshots, optimistic-concurrency by `version`.
- `guest_migrations (id uuid PK, user_id, guest_profile_id, snapshot jsonb, status, created_at)`
- `audit_events (id uuid PK, user_id, kind, detail jsonb, created_at)`
- `app_config (key PK, value jsonb)` — e.g. `cloud_wallet_enabled=false`.

RLS: every table `user_id = auth.uid()` for select; wallet/ledger/ownership
writes only through `security definer` RPCs; `account_roles` readable by its
owner only, writable by nobody through the API. New-user trigger creates
profile + wallet (350) + ROBOT ownership atomically.

## 4. Legacy migration plan

1. **Local profiles (existing browsers):** balances and owned fighters are
   preserved verbatim. Removing the seed means: no refill ever again; a
   profile that previously received 12,000 keeps its *current* balance (we do
   not claw back — destructive resets are prohibited by the brief). The stale
   `ownerPlaytestAcSeed` marker remains readable by `sanitize()` for one
   release so old saves never break, but nothing consumes it.
2. **Guest → account:** on first sign-in the client snapshots the local meta
   state and offers migration. The snapshot is stored as
   `guest_migrations(snapshot, status='pending-review')` and marked
   *unverified legacy data*: it restores preferences/progress, and is only
   promoted to verified wallet/ownership by the (currently disabled) server
   policy — never by trusting localStorage arithmetic.
3. **Rollback:** flipping `OWNER_PLAYTEST_*` constants back restores the old
   behavior exactly (the fenced-switch design is preserved); DB rollback SQL
   ships beside the migration.

## 5. Threat model & trust boundary

| Threat | Mitigation in this phase |
|---|---|
| localStorage tampering → fake AC/ownership | Accepted for the *local* wallet (single-player cosmetics of progress); explicitly **not** accepted as cloud proof. Cloud wallet issuance disabled until receipts exist. |
| Reward replay (duplicate callback/reload/retry) | Persistent claim keys: `resultGold.meta.id` recorded in meta state (`claimedMatchIds`, capped) + DB unique `claim_key`. |
| Ctrl+Shift+F8 / console `apexLaunchArsenalLab()` privilege escalation | New `APEX_ADMIN_AUTHORITY`: role derives from authenticated cloud role (`account_roles`/app_metadata) or a **dev-build-only** env flag. Production without a verified admin identity fails closed with visible denial. Shortcut remains, authorization does not come from the keyboard. |
| Admin session contaminating economy | Lab already pays 0; owner-test-active matches now also pay 0; admin selection override never writes ownership and load-time sanitize reverts unowned selections. |
| Account cross-talk | RLS `auth.uid()` on every table; no service-role key in frontend (only anon key + user JWT). |
| OTP/OAuth abuse | Supabase built-in rate limits; no custom password auth. |
| Fake cloud success | Adapter is env-gated: without `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` the UI honestly reports "Cloud not configured / local guest". No simulated logins. |

**Explicit limitation:** gameplay runs in the browser, so client-reported
victories are not cheat-proof. The local wallet therefore stays a *local*
progression system in A1; the server schema/RPCs are ready but issuance stays
disabled (`app_config.cloud_wallet_enabled=false`, client flag mirrors it)
until a future phase adds validated match receipts. This is the safe boundary
required by the brief §5.

## 6. Deployment dependencies (owner actions — see final report)

1. Create a Supabase project; run `supabase/migrations/0001_*.sql`.
2. Enable Google provider + Email OTP in Supabase Auth; set Site URL/redirects.
3. Set Netlify env: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (public anon key only).
4. Grant admin: insert owner row into `account_roles` via Supabase SQL editor.
5. (Dev only) `VITE_APEX_DEV_ADMIN=1` enables admin in `vite dev` builds; it is compiled out of production behavior by the `import.meta.env.DEV` check.

Until steps 1–3 exist, A1 ships as: correct local economy + guest profile +
honest offline Account Center + gated admin + skill details. No dead fake
login buttons: cloud actions render their real unavailable state.
