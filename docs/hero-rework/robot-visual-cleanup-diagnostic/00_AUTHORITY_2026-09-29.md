## Source-audited render facts

These are facts, not hypotheses:

### Shared source scale

Both golden HTML and production currently use:

- authored head space: `1280`
- `HS = 172`
- `HSC = HS / 1280`
- segmented raster cache `SR = 820`

Therefore “production uses a lower SR asset” is NOT established as the cause of softness.

### Pipeline difference

The golden HTML does additional display-aware rasterization:

- it computes output using viewport fit / camera scale;
- caps and uses `devicePixelRatio`;
- renders the dynamic rig into a dedicated render texture sized from effective display scale and DPR;
- then composites/blits that texture into the final canvas.

Current production `robotPresentationRuntime.js` instead draws the segmented 820 px sprite pieces directly through the game/world canvas transform.

This makes a Robot-only sampling/rasterization difference a plausible cause of perceived softness, especially on high-DPI displays or when the game canvas is CSS-scaled.

This is a hypothesis to test, not permission to rewrite the global APEX canvas.

### Current segmentation path

Production rebuilds the vector source at 1280, then creates segmented 820 px canvases through `destination-in` / `destination-out` masks.

Tight masks cutting anti-aliased strokes, mask overlap/gaps, subpixel resampling, or light/dark alpha fringes are plausible causes of edge dirt / clipped-looking seams.

Again: diagnose first.

## Diagnostic protocol

Use one deterministic production Chromium environment and one deterministic HTML-reference Chromium environment.

For comparisons:
- same browser build;
- same viewport;
- same `deviceScaleFactor`;
- same approximate physical Robot size on screen;
- no camera shake;
- no unrelated opponent skill VFX;
- ROBOT vs ICE, AI disabled.

Run at minimum at DPR 1 and DPR 2.

### D1 — background contrast matrix

Capture the same static Robot state against:

1. near-black;
2. neutral mid-gray;
3. near-white.

Do this for:
- idle;
- A2 locked;
- immediate post-projectile-impact.

Use diagnostic background override only; do not commit global arena recoloring.

Purpose:
- find alpha fringe that flips visibility by background;
- distinguish true source/mask dirt from background perception.

### D2 — zoomed edge inspection

For each background, create 4x or nearest-lossless diagnostic crops of:

- left/right outer caliper silhouette;
- cheek/chin boundary;
- pivot disc boundary;
- crest/core slot;
- eye/socket boundary;
- one impact-side edge.

The zoom is for inspection only and must not be used as production rendering.

Classify each observed defect as one of:

- MASK_CUT
- MASK_GAP
- ALPHA_FRINGE
- SUBPIXEL_SOFTNESS
- RESAMPLE_SOFTNESS
- AUTHORED_PARTICLE
- WORLD_EFFECT
- NO_DEFECT

### D3 — impact isolation

Capture the exact same controlled projectile hit twice in diagnostic mode:

A. normal production effects;
B. Robot rig + local stress/flash only, with world mechanical chips/sparks temporarily hidden by the diagnostic harness, not by production code.

If the ugly fragment remains in B, the defect is in sprite/mask/local compositing.
If it exists only in A, inspect the world particle spawn/shape/coordinate behavior.
If neither shows the owner's symptom, document that the earlier issue is no longer reproduced after the previous RVC fixes.

### D4 — sharpness A/B

Compare golden HTML vs production at matched physical Robot size.

Measure or record:
- CSS/world displayed width and height;
- backing-buffer pixel coverage;
- DPR;
- any intermediate raster dimensions.

Then produce production-only A/B candidates:

A. current production path;
B. Robot-only supersampled/offscreen path at effective 2x backing resolution;
C. optional adaptive DPR path capped at 2 only if B is clearly better.

Do not alter gameplay scale.

Judge at 100% screenshot scale, not zoomed browser screenshots alone.

A useful sharpness fix must:
- preserve silhouette geometry;
- preserve anti-aliasing quality;
- reduce softness at normal viewing size;
- not introduce shimmer during movement;
- not create visible mask seams;
- have bounded performance cost.

### D5 — movement stability

If any raster/sampling change is proposed, record a short real-game movement clip.

Reject the fix if sharper static frames introduce:
- crawling edges;
- shimmer;
- temporal aliasing;
- inconsistent layer registration;
- noticeable frame-time regression.

## Conditional fix rules

Only commit a production visual fix when the diagnostic identifies a reproducible cause.

Preferred order:

1. correct mask geometry / overlap / padding if masks actually cut visible source;
2. remove alpha fringe at the segmentation/compositing stage if proven;
3. normalize subpixel placement only where it does not break HTML motion;
4. add Robot-only supersampled render target if matched-size A/B proves production sampling is materially softer.

Do NOT change `SR` blindly just because a larger number sounds more HD.

If current production is only mildly softer because it matches the rest of APEX and the supersampled path offers little perceptual gain, keep current production.
